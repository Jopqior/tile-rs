# Released Rust backend → PTO frontend probe (macOS ARM)

Session archive: [补录新版 Rust→PTO→camodel 验证与 NPU 资源申请草稿](https://github.com/Jopqior/tile-rs/issues/61).

Status: **real compiler-produced Rust→MLIR→current PTO emitter succeeds** with a *release-matched* Rust DSL. This is frontend generation evidence, **not** proof that ptoas accepts the PTO or that its kernel runs in camodel/on an NPU. No MLIR/PTO fixtures, private binary edits, or source patches were used in the successful run. The kernel in `prototypes/rust-pto-ascend/frontend/add_generated.rs` is `add_generated(a: *const f32, b: *const f32, out: *mut f32)`: a 1×256 f32 load/load/add/store using the published macro's documented raw-pointer input shape. Its ABI has three pointers in `a,b,out` order.

The macOS-14 ARM workflow builds the **current** CLI on stable; installs published `rustc_codegen_tile` v0.0.2+nightly-2025-08-04 through `tile install rustc_codegen_tile` (manifest SHA-256 `70fffed473aa2d5c3f51bcc04caf9d18e0379188e764689ed52be0c373926891`); installs exact nightly-2025-08-04 with rustc-dev, llvm-tools, rust-src; and checks out **unmodified** `yijunyu/tile-rs` commit `c3c8ec0169bd02757b51370ba9c6ec3b116b833d` (the published release tag commit) for `TILE_STD_PATH`, including its sibling `tile_std_macros`. The public CLI/emitter and Rust kernel are from the current checkout. `-t msl` selects `metal` only to save neutral compiler MLIR on macOS; the backend's native `-t pto` requires CANN there. The second CLI invocation emits PTO from that saved MLIR with the **current-source open PTO emitter**, not the released backend's optional target source.
